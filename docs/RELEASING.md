# Выпуск SDK 2.0.5

Версия пакета должна совпадать в его manifest и lockfile. Версии нативных SDK должны совпадать с release/native-lock.json и нативными зависимостями моста.
Инструкции установки и настройки приложения находятся в README.md;
изменения интеграции звонков — в docs/MIGRATION_2.md.

1. Согласуйте package.json, package-lock.json, Podspec, Gradle и release/native-lock.json: версия пакета 2.0.5; версии native SDK — из release/native-lock.json.
2. В native-lock.json зафиксируйте точные коммиты Android SDK 2.0.4 и iOS SDK 2.0.3.
3. Выполните typecheck, JavaScript/Expo/publication tests и нативные consumer builds.
4. Сформируйте native/ командой `npm run release:stage` с нативными исходниками из зафиксированных коммитов. Maven-артефакты загрузите командой `node scripts/fetch-native-maven.mjs /tmp/pushpilot-maven`: в пакет должны попасть опубликованные байты, а не повторная сборка той же версии.
5. Перед npm-публикацией `npm run release:verify-ios` проверяет публичный iOS-тег, его соответствие native-lock.json и наличие SDK и Extension в индексе и specs CocoaPods CDN; `npm run release:check` проверяет содержимое npm-пакета.
6. Workflow `Prepare / publish React Native SDK` публикует пакет только при ручном запуске с `publish: true` и git-тегом версии. Обычный push публикацию не запускает.

CI проверяет опубликованные нативные зависимости и реальные iOS-установки с обычным autolinking, без Git/path-подмен в Podfile. Проверка обновления начинается с npm-пакета 2.0.3 и сохраняет посторонние версии из Podfile.lock.

## Обязательные условия выпуска

1. Сохраните прежние локальные правки отдельными коммитами в отправленных ветках; синхронизируйте основные каталоги с main.
2. Подготовьте версии, lockfile, runtime metadata, документацию и генерируемые файлы до финального коммита. Отправьте все коммиты выпуска.
3. Дождитесь успешного CI PR, затем успешного CI main после merge.
4. Создайте новый тег vVERSION на проверенном коммите. Существующие опубликованные теги не перезаписывайте.
5. Дождитесь успешных проверок тега. До этого GitHub Release не публикуется.
6. Опубликуйте стабильный GitHub Release и проверьте последующие workflow, если они запускаются публикацией.
7. Проверьте все затронутые основные каталоги и worktree: `git status --porcelain --untracked-files=all` должен быть пуст, все коммиты должны быть доступны в origin.

Красная или незавершённая обязательная проверка блокирует публикацию. Наличие незакоммиченных файлов блокирует публикацию и завершение работы. Публикация пакетов в реестры выполняется отдельной штатной процедурой; GitHub Release сам по себе её не запускает.
